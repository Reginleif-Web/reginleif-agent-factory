# Agent Factory database

The application database of Agent Factory. Binding sources: [architecture.md](architecture.md) (decisions D1-D34, the
task states, state ownership), [governance.md](governance.md) (the Decision Registry and the regulation, whose tables
are listed below) and the task specification section 4. Status: design. Types are PostgreSQL 16. Temporal keeps its own
two databases on the same server; they hold Temporal's tables, not described here, and only their account, ownership and
backup are (see "The Temporal databases"). "Call" marks a design choice made here, open to veto. The schema
is written in Drizzle (D27): the table definitions live in `factory/db/schema/` and are the source of the migrations
(see Migrations and backup); this document is the design the definitions follow.

## Conventions

- Primary keys are `uuid` (v7, generated by the server, so they sort by time). Exceptions: `task_events.seq`,
  `outbox_events.seq`, `audit_log.seq`, `notifications.seq` and `messages.seq` carry a `bigint generated always as
  identity` next to the uuid, for cursors and relay order.
- **Stream cursors.** An identity number is taken when a row is inserted, not when its transaction commits, so a reader
  that remembers "the highest number seen" can skip a row that commits late, and one number over several tables is not an
  order at all. So each stream (`task_events`, `audit_log`, `notifications`, `messages`) has its own cursor, and its
  table has `commit_xid xid8 not null default pg_current_xact_id()` next to `seq`. A reader returns only rows whose
  `commit_xid` is below `pg_snapshot_xmin(pg_current_snapshot())` (every transaction older than that one has ended, so
  no row can still appear below the horizon), ordered by `(commit_xid, seq)`. The cursor is the pair of the last row
  returned, written as an opaque string that names its stream; the client keeps one per stream and never reads or
  builds it. A cursor of another stream, or one that does not parse, is refused `bad_cursor`. A row is seen only after
  every older transaction has ended (a delay of one transaction's length, in the usual case milliseconds), and never
  twice or not at all. Indexes `(commit_xid, seq)` on these tables. `outbox_events.seq` is an order only: the relay reads
  by `state` and the lease, never by a cursor, so it cannot lose a row. The rule is stated in [api.md](api.md) (Events and
  pagination); every place that reads a stream follows it.
- Times are `timestamptz`, set by the database (`now()`), never by a client. Enums are PostgreSQL enums or `text` with a
  `check`; a new value is an expand step (see Migrations). JSONB columns have a `check (jsonb_typeof(...) = ...)` and a
  schema validated in `factory/contracts/` before the write.
- Every mutable table has `row_version bigint not null default 1` and `updated_at`. Every foreign key is `on delete
  restrict`: nothing cascades, history is never removed by a parent's removal.
- Secrets never enter any column (`agents.configuration` holds references such as a credential name, never a value).
  A write whose JSON contains a key on the secret-name list is refused by the contract layer.
- Workflow memory names are the camelCase form of the column names (`block_kind` and `blockKind`, `resume_to` and
  `resumeTo`, `pause_requested` and `pauseRequested`).

knows. The registry is off by

## Rights tables

**Where a right can live, and how each closes** (the one list the critical reaction and the measures follow). Every
place has a closing that does not depend on finding the right row by hand:

| Place | Closes by |
|---|---|
| a role (`roles`, through `role_assignments`) | the gate: an agent with an open `rights_suspensions` row has no role in the check; the assignment row is not edited; a measure ends it by a new `role_assignments` row |
| a grant (`right_grants`) | the same transaction ends every open grant of the agent with `ended_by = 'critical'` and the suspension id; the gate refuses the rest |
| a permission record (`registry_records` kind `permission`) | the owner's own scope-based act; it is not edited; the gate refuses the agent, and `consumed_at` is not set by a refused call |
| an API token of the run (`api_tokens`) | the same transaction sets `revoked_at` on the run's tokens |
| a live worker session (a running process, its Claude or Codex session) | an outbox row `stop_run` in the same transaction; the worker ends the run by its `execution_id` (the whole process tree) and ends the session; delivered at least once, applied once. A worker that does not answer within `stop.orderSeconds` is bypassed on the same machine: the control component writes the runner's stop request file itself and the runner ends the run; a worker executes pending stop orders before anything else when it starts |
| a sandbox profile of the Codex adapter | a snapshot: it cannot be taken back from a running process, so it is closed by the kill of the run by its identity. **A run whose profile holds a right that ends.** When a grant ends (task end, revocation, critical), a permission record
is revoked, a regulation version replaces the one that held a right, a role assignment ends or is replaced, or an agent is
suspended, the same `af_control` transaction writes one outbox `stop_run` row for every live run whose
`profile_rights` contains that right (found by the right's id or by the role version); runs whose profile does not contain
it go on. The task continues with a new attempt and a profile built from the then rights.

The suspension row, the grants' ending, the token revocation, the `audit_log` row `rights.suspend`, the `stop_run`
outbox row of **every live run of the agent** (all configurations of the same `agents` row, one row per run) and the
`notify` outbox row for the owner are written by `af_control` in one transaction: either all exist or none, so there is
never a stopped run with open rights or open rights with no stop order. While an agent has an open `rights_suspensions`
row no new run of it starts (the start of a run reads the gate), until the restore.

The API route never sets `accepted` or `refused` itself for a poll whose arbiter is `hub`. |

Indexes: `(commit_xid, seq)` on `messages` (the stream cursor, see Conventions) and `(conversation_id, seq)` (a
conversation's history); `(state, created_at)` on `polls`; `(created_at)` where `state = 'pending'` on
`poll_answer_requests` (the hub's catch-up and the retry read it); unique `(device_session_id, idempotency_key)` on
`poll_answer_requests`; `(device_id)` where `revoked_at is null` on `device_sessions`.

Setting in `settings`: `device.codeTtlSeconds` (life of a one-time code; a starting value).

Other changes: `audit_log` gets the nullable `device_session_id` by `alter table` (an expand step), set on every row a
device session caused; `api_tokens.role` gets the value `hub` (the owner's hub fork: it may write messages, polls and
session states and nothing else; one `session_ref`-free token, bound to the one hub).

Creation order. Every key target exists in 0001 and 0002. In 0003: `devices` and `device_sessions` first (the keys of
`confirmations` and `task_decisions` need them), then the tables of 0003 as before, then `conversations`, `messages`,
`polls`, `poll_answer_requests` (they point to `projects`, `tasks`, `task_decisions`, `task_artifacts` only by id list, `device_sessions`), then
`audit_log.device_session_id` and the `hub` role value by `alter`.

Constraints (the design decisions; each has a check in [testing.md](testing.md)):
- **One active controlling lease per platform:** a partial unique index on `robot_leases (robot_id)` where `ended_at is
  null and revoked_at is null`. A second one cannot be inserted; the old one is ended first (`robot-lease`).
- **A lease ends before the next begins (robotics.md Table 1):** a trigger refuses a new lease for a platform unless the
  previous lease is `ended` there: its `end_confirmed_at` is set by a confirmed `rep(h)` of the robot, or its bound
  `min(last_answer_at + robotics.heartbeatSeconds, expires_at)` plus the clock tolerance has passed (a lease whose
  challenge was never answered has the bound 0), else `lease_ending`. The gateway answers a challenge only for the active
  lease, once per counter, and signs no time; ending a lease stops the answers. An unknown outcome, a safe stop, a stop
  request or an agent change sets `ended_at` and `recalled_at` on every unfetched command in the same transaction
  (`robot-lease`, `robot-unknown`; model check I1 to I5, testing.md).
- **One gate-3 reference per lease and per command:** `robot_leases` and `robot_commands` each carry `qualification_id` and
  `admission_id` under the check `num_nonnulls(qualification_id, admission_id) = 1`; a trigger requires a command's pair
  to equal its lease's, and a lease of a qualification ends when that qualification is suspended or revoked. A command of
  an ended, expired or recalled lease is refused, and the commands route returns only the commands of the active lease
  that are neither expired nor recalled (`robot-command`, `robot-five-gates`).
- **One receipt per command id:** unique `robot_receipts (command_id)` and unique `robot_commands (command_id)`; a repeat is
  deduplicated, never run twice (`robot-command`). `robot_commands.sequence` is unique per lease and assigned by the gateway.
- **Experiments and evidence are immutable:** `update` and `delete` on `robot_experiments` once started, on
  `robot_evidence`, `robot_qualifications`, `robot_stages`, `robot_reviews` (except the one verdict of a `pending` review),
  `unattended_policies` and `robot_safety_events` are refused by a trigger and by the grants of the application role (see
  Immutable rows and soft delete); a correction is a new row (`robot-evidence`).
- **Record life is robotics.md Table 2, in the database:** a record whose truth depends on another is inserted pending
  (`REVIEW_PENDING`, review verdict `pending`, `reviewer_run_id` null) and granted nothing; only its deciding step makes it
  final, in a trigger that runs at that step. There are no deferred constraint triggers and no trigger that asks for a
  final value at insert. A column set by a later step (`reviewer_run_id`, `verdict`, `used_at`) is null before it, set once,
  immutable after; who may write which step is a grant of the application role, one role per actor of the table. A row that
  relies on a final row (a qualification on its review, a lease on its qualification or admission) checks the final state,
  hash and version again at its own insert (`robot-qualification`, `robot-evidence`).
- **A review has one subject:** `robot_reviews.subject_kind` is `evidence_set`, `experiment_plan`, `stage_exit` or
  `unattended_policy`, and a check constraint sets exactly the columns of that kind (`experiment_id` only for the plan,
  `robot_id`, `configuration_id` and `stage` only for the exit, `policy_hash` only for the policy, evidence rows in
  `robot_review_evidence` only for the evidence set and the exit). `content_hash` and `subject_version` cover the reviewed
  content. Table 2 says which step checks what: the insert only the columns and the hash, the attach of the reviewer run its
  independence (run and provider differ from the executor's, D20), the verdict that the hash and version still equal the
  subject's and that the covered evidence rows are exactly the listed ones. A review that is not final and confirming, or a
  hash that no longer matches, refuses the row that relies on it (`review_invalid`).
- **A qualification and a stage exit rest on their evidence and review at the deciding step:** every identifier of a
  qualification is `not null`; the `QUALIFIED` row names its `REVIEW_PENDING` row, and the checks of Table 2 run at its
  insert (`evidence_missing`, `qualification_invalid`, `review_invalid`, and `stage_exit_invalid` for the exit;
  `robot-qualification`, `robot-evidence`). The robotics review table is used, so that this migration does not depend on
  0014's `qualification_reviews`.
- **An admission is bound to one experiment and one lease:** `robot_admissions.experiment_id` is unique; `plan_hash`
  equals the `content_hash` of its final `experiment_plan` review; the Admission rows of Table 2 give the insert checks and
  the `used_at` set in the lease insert. A trigger refuses a command row whose `admission_id` is expired, not the lease's,
  of another experiment, of a stage other than the stage reached or the next, or whose limits exceed the admission's. An
  admission gives no qualification and no right outside its experiment, and a skill's state is not changed by it. It has
  no evidence minimum (`robot-qualification`, `robot-five-gates`).
- **A stage opens only on a standing exit:** a trigger refuses an experiment of stage N, or a `robot_stages` row, unless
  stage N-1 has a standing exit for the platform, and D0 has no predecessor. A standing exit is a `robot_stages` row of
  the current configuration, or of an earlier one when every later configuration's `touches_stage` is greater than that
  stage; the rows of older configurations are kept as history and nothing is deleted. The evidence kinds of a stage are
  those of the Evidence column of the stage table (`inventory` for D0, `physical` for D1 to D7 and D10, at least one
  simulation and one physical for D8, at least one physical for D9); the checks are the Stage exit rows of Table 2.
- **Presence and attendance are two columns, not one fact:** `robot_leases.presence` (`interlock`, `confirmation`) records
  how people in the zone were covered, `robot_leases.attendance` (`press`, `policy`, `confirmation`) how the unattended
  case was covered. `confirmations.reasons` is a non-empty subset of `people_possible` and `no_unattended_policy`, both
  allowed in one row. A start press is its own row, `robot_start_presses`, and **only it records that a person attends**;
  a confirmation of possible presence never counts as attendance. The lease insert recomputes the reasons the start needs
  and refuses a confirmation that lacks one (`confirmation_invalid`), refuses people possibly present with neither a closed
  fresh interlock nor a confirmation listing `people_possible` (`people_may_be_present`), and a start with no start press,
  no valid policy and no confirmation listing `no_unattended_policy` (`unattended_policy_missing`); the first press, the
  second press and the consumption are the Start confirmation rows of Table 2 (`robot-safety`, `robot-owner-load`).

## Revisions and the version of a row

- **Task row.** `tasks` has two writers: the API (create, archive, soft delete; title and description are never edited:
  a requirement change is a revision) and `PersistTaskEvent` (status, `current_revision`, `workflow_run_id`,
  `block_kind`, `block_reason`, `block_handler`, `resume_to`, `pause_requested`, `stopping`, `end_unconfirmed`, `assigned_agent_id`,
  `completed_at`). Every update is `update ... set row_version = row_version + 1 where id = $1 and row_version = $2`;
  zero rows is a conflict. The workflow writer re-reads and retries once; it never overwrites a newer status. An API
  client sends the version it read (`If-Match`) and gets `409 version_conflict` otherwise.
- **Revision.** A `revise_requirements` decision inserts the new `task_revisions` row in the same transaction as the
  decision (the number is `max + 1` under the task row lock). `tasks.current_revision` moves only when the workflow
  applies the decision. A refused decision leaves its revision row as history. A decision that carries a revision number
  older than `current_revision` is refused `revision_stale` (D14 and the architecture's revision rule).
- **Status moves** are checked twice: the workflow validates a move against the transition table, and a trigger on
  `tasks` refuses a status change that is not a row of the table (the table is the test data and a lookup table
  `task_transitions(from_status, to_status)` loaded by a migration, which includes the cancel, pause and block rows of
  the architecture). A final state never leaves: FAILED too, work goes on in a new task (call, see Child tasks).
- **BLOCKED exit** is decided by `block_kind` (architecture): `scope` to PLANNING; `dependency` to READY; `execution`,
  `usage_limit`, `agent_question` to ASSIGNED; `check_environment` to VERIFYING; `rework_limit` to REWORK_REQUIRED; the four physical kinds of D34 (`safe_stop`,
  `physical_unknown`, `maintenance`, `quarantine`) to ASSIGNED, only after a new check and a new permission to move, never
  as a retry of the physical operation (temporal.md, BLOCKED kinds). The table `task_transitions` carries these rows and
  the trigger checks the pair of kind and target. Only the progress exit (resolve) is decided by the kind: cancel
  (CANCELLED, CANCELLING), pause (PAUSED) and revise (PLANNING) leave BLOCKED whatever its kind (migration 0011).
- **Block handler.** `block_handler` says who the block waits for and is set with the kind when the task enters BLOCKED,
  by a rule in code, never by an agent: `scope` and `agent_question` enter with `owner`; the other five kinds
  (`dependency`, `execution`, `usage_limit`, `check_environment`, `rework_limit`) enter with `chief_engineer`, except when
  the cause itself needs the owner (a new requirement, scope or cost, a dangerous operation, an owner's own credential such
  as a login), which enter with `owner`. The physical kinds of D34 enter with `chief_engineer` (`safe_stop`,
  `maintenance`; `physical_unknown` too: the chief engineer observes first, and a person is asked only when no allowed
  observation remains, as a dependency with the smallest human part, never as a decision of the owner or a critical
  notice) and `quarantine` with `owner`. The chief engineer resolves a block it handles by a `resolve_block` row of
  `task_decisions` with `engineer_run_id` (the choices of the kind, except one that raises a cost, token or time budget or does a dangerous
  operation, which is the owner's; a routine physical decision with no block is a `physical_decision`, see Run roles and independence), or calls the owner with the choice `call_owner`: that row
  leaves the status as it is, sets `block_handler = 'owner'` once, and raises the owner's notice. The owner may resolve
  any block whoever handles it, and a resolution by the owner wins over a concurrent one of the engineer (the row version
  decides, the loser is refused `block_handled`). The owner's notice is raised only when `block_handler` is `owner`; a
  `usage_limit` block reaches the owner only when it stops everything (no enabled agent of any provider can run). With the
  chief engineer unavailable a block it handles waits and nobody is told (G13). `block_handler` changes only by the
  entry into BLOCKED and by `call_owner`; leaving BLOCKED clears it with the kind.
- Per-row versions exist on `projects`, `tasks`, `agents`, `workers`, `task_runs`, `routing_rules`, `api_tokens`,
  `device_sessions`, `settings`. Immutable tables carry none.

  version row), `task_dependencies` (except the removal mark), `task_artifacts` after `confirmed` (except the removal

  `regulation_versions` (their status columns change under audit), `registry_links`, `registry_embeddings`,

A trigger raises on `update` or `delete` of
  the immutable columns, so the rule holds even for a mistake in code.
- Soft delete (`deleted_at`) exists on `projects`, `tasks`, `agents`, `routing_rules`: the owner marks a row; every list hides it unless
  asked; unique names apply to live rows only (partial unique indexes). A task can be soft deleted only in a final state;
  a project only when archived and with no active task (a standing task, below, is not an active task). A standing task
  is never soft deleted. Rows with history (`task_runs`, `workers`, events) are never
  deleted: `workers` are `disabled`, `api_tokens` are revoked.
- No row is ever hard deleted (D24). There is no purge account.

## Cleanup on command (D24)

Nothing is deleted by itself, and the history of decisions and events stays for good. The owner's cleanup command for a
task in a final state (a standing task is never in one, so it is never cleaned), and the chief engineer's grant for its
part (G15: nothing unsaved), remove only files: the stored logs and artifacts (the `task_artifacts` row stays with its key and
checksum, `upload_state = removed`), the execution folders on the machine and the worktree. It refuses a task that is
not final, an artifact of a task awaiting approval, and a worktree with unpublished changes; the owner may force the
last one (a dangerous operation, two presses). The API records the command as a `task_events` row and an outbox row of
kind `cleanup`. There are no `retain_until` columns. Idempotency keys, done outbox rows, notices and the audit log stay
too (they are small); the backup grows with the history.

## Dependency cycles

Adding an edge runs in one transaction under `pg_advisory_xact_lock(hashtext('af-deps'))` (edge changes are rare, so one
lock is enough): a recursive query walks `depends_on_task_id` from the new target over live edges and refuses with
`409 dependency_cycle` (the path in the error) if it reaches `task_id`; the self-loop `check` covers the trivial case. A
constraint trigger on insert repeats the walk as a backstop. A removed edge frees the cycle. Dependencies are resolved
anew whenever a BLOCKED task returns to READY (architecture), and `ResolveDependencies` reads only live edges.

## Child tasks

`origin_type` enum: `owner`, `decomposition`, `agent_proposal`, `continuation`, `standing` (below); `origin_task_id`, `origin_run_id`
(required for `decomposition` and `agent_proposal`), `origin_actor`. `depth int not null`, with `check ((parent_task_id
is null) = (depth = 0))`; a trigger sets `depth = parent.depth + 1` and refuses a value above `max_child_depth`. A
count limit per parent (`max_children_per_task`) comes from the same policy. A child may point to a parent only in its
own project. An `origin_run_id` must belong to the `origin_task_id`.

- **Inside the requirements (D19, call).** A proposal of kind `decomposition` is inside the requirements when every id in
  `covers` exists in the parent's current `acceptance_criteria` and the limits hold: depth, count per parent, and the
  parent's budget (spend is rolled up over a task and its descendants, so a child's spend counts against the root's
  `max_cost` and `max_tokens`; the sum is taken over the `task_runs.usage_metrics` keys `tokens_in + tokens_out` and
  `cost_estimate` of every run in the root's tree; a run without the keys makes the spend unmeasured and the proposal
  stays open, reason `budget_unmeasured`). `CreateChildTasks` then creates the child (`origin_type = decomposition`) without the
  owner. Everything else, every `requirement_change` and `suggestion`, is a `task_proposals` row in `open` for the owner;
  accepting it creates a child with `origin_type = agent_proposal`, declining keeps the row.
- **FAILED is final (call).** Work goes on in a new task created by the owner with `origin_type = continuation` and
  `origin_task_id` set to the failed task; nothing is copied, requirements are the owner's.

## Standing tasks

A run of the chief engineer for an ordinary Claude session has no task of its own (a session is not a Factory task),
yet `task_runs.task_id` is required, and so are the limits, the audit and the cleanup that hang on a task. One mechanism
serves it (call): a **standing task**, a `tasks` row with `origin_type = 'standing'`, one per project (a partial unique
index on `project_id where origin_type = 'standing'`); a session with no project uses the standing task of the system
project `_factory`, seeded by migration 0007 (the enum value exists since 0002). `right_requests.handling_task_id`
names the task whose run answers a request: the requesting task for a Factory task, the standing task of the session's project (or `_factory`) for an
ordinary session; the request row itself names the session, never a task of it.

| Aspect | Rule for a standing task |
|---|---|
| State | status `RUNNING` from its insert and never another: a trigger refuses any transition, a `task_decisions` row of any kind but `physical_decision`, a revision above 1 and a `workspaces` row; no workflow is started and no `start_workflow` outbox row exists (`workflow_id` is only the key that binds its runs) |
| Where it does not appear | not scheduled and not in task lists or counts of the owner's work; it is not an active task (a project can be archived with only it left, and then it is archived with the project); never soft deleted; `completed_at` stays null; `CleanupWorkspace` and the cleanup command never meet it (no workspace) |
| Limits | attempt, rework and auto-fix counters and per-task budgets do not apply to it; concurrency of agents and workers still does, and the run costs and tokens are rolled up per request in `right_requests` and on the standing task for the report of the owner |
| Runs | its runs have role `chief_engineer` and a `participant` of the session; a run ends when the answer is written; the independence and run-role rules below hold unchanged |
| Rights | a grant for an ordinary session ends with the session, not with the task (governance.md); the standing task never ends, so it closes nothing |

## Run roles and independence

`task_runs.role` fixes who did what. Rules held in the database, not in a prompt: a `task_approvals` row of type `manual`
requires an owner actor (agents have no token that can decide); a `task_reviews` row requires a `run_id` of role
`reviewer`, and the provider of its `reviewer_id` agent must differ from the provider of the agents of the `implementer`
runs it reviews (D20); a settling run (`disputes_review_id` set) is a fresh run that is not an implementer run of the
task. When no enabled agent of another provider exists the task goes to BLOCKED (`check_environment`). A `reviewer` or
`planner` run cannot write a `task_revisions` row (`author_id` is an owner). A `chief_engineer` run answers a right
request, resolves a block it handles, or takes a routine physical decision; it belongs to the task named in
`right_requests.handling_task_id`: the requesting task, or the standing task of an ordinary session (Standing tasks,
above), or the BLOCKED task whose `block_handler` is `chief_engineer`, or, for a routine physical decision, the standing
task of the project or the physical task that an assignment, lease or experiment of the platform names. It writes no
revision and no artifact; its decision rows are only the `resolve_block` of Block handler and the `physical_decision`
below, and a trigger refuses a `chief_engineer` run on a task that has neither a request naming it, nor that block, nor
a platform of D34 it may decide for.

**The chief engineer's routine physical decision (D34).** Assignment, release, admission, qualification bookkeeping and
the choice of a configuration's `touches_stage` are routine and need no block. They run as the chief engineer's own run
(role `chief_engineer`, never an executor's or a reviewer's of the same subject) and leave one `task_decisions` row of kind
`physical_decision` with `engineer_run_id`, channel `api`, and a payload that names the platform and one `decision`:
`assign`, `release`, `admit`, `qualify`, `bookkeeping`, `reenrol` or `call_owner` (`reenrol` records a platform's
re-enrolment after its persistent memory was lost, with the hardware check named in the payload; it is the only thing
that lets that platform accept a lease again, and it is not a qualification). A trigger checks the payload and that the task
is the standing task or the physical task of that platform; the effect (the `robot_assignments`, `robot_admissions`,
`robot_qualifications` or `robot_configurations` row, or the platform's re-enrolment mark) is written in the same transaction; the row is `applied` at insert.
Its limits stay: its own run, the owner's list of choices it may make (G15), `call_owner` for everything the owner
holds (`owner_only`), and no `physical_decision` raises a budget or does a dangerous operation. A review of the same
subject is still another run and provider (below).

**One rule for every review a decision relies on.** A review (a `task_reviews` row, a `qualification_reviews` row, the
independent check of a measure, the classifier review of an incident, a `robot_reviews` row) counts for a decision only when a trigger finds it
(a) tied to the same task or incident as the decision (a `robot_reviews` row: to the same subject, with the same identifiers and `content_hash`), (b) in the verdict that supports it (`confirmed` for a
qualification, `pass` for a task review), and (c) authored by a run and an agent that are not the subject or the
author of what is judged; of another provider where D20 or the personnel rules ask for it. The decision's row holds the
review's id, never a copy of its verdict, so no row can lean on an unrelated or a failed review.

`execution_policies` is versioned and immutable: `id`; `project_id` nullable (null is the global default);

`allowed_repositories text[]`; `network jsonb`; `git_operations text[]`; `confirmation_required text[]`;

## Notifications

`notifications`: `id`; `seq` identity unique and `commit_xid xid8` (the stream cursor, see Conventions); `event_type` enum; `dedup_key text` (for example `worker_offline:<worker id>`,
`task_blocked:<task id>:<blocked_at>`); `task_id`/`worker_id` nullable; `state` enum (`open`, `resolved`);
`occurrences int`; `first_raised_at`; `last_raised_at`; `delivered_at`; `resolved_at`. Unique index on `dedup_key where
state = 'open'`: raising an open notice only bumps `occurrences` and `last_raised_at`, so one outage gives one message.
A resolved notice allows a new one. The liveness activity of `MachineLivenessWorkflow` resolves the open `worker_offline`
notice of a worker when that worker's heartbeat returns (`state = 'resolved'`, `resolved_at` set), so each outage raises its
own notice: the next silence of the same worker creates a new row, and continued silence only bumps the open one. The status a recovering worker gets is derived, not stored: `online` when its `contract_version` is in the supported range (the current contract, or the one before it when the current is above 1: the same rule as the API header check in `factory/api/handlers/tasks.ts`, shared as `factory/contracts/contract-range.ts`), `outdated` otherwise, so recovery never writes plain `online` over an unsupported contract. The contract version is already a column of `workers`, so this needs no migration.
Repeating an open notice is the setting `notice.repeatHours`, empty (never) until
its phase (see Open, decided in its phase). Index `(commit_xid, seq)` (the stream cursor: a client reads only the
notices older than the oldest running transaction, see Conventions).

Event types: the eight of spec 16.2 and the notices the other documents raise. A machine going offline is the same
event as a worker going offline (`worker_offline`: the worker is the machine's process).

| `event_type` | Raised when | Source |
|---|---|---|
| `worker_offline` | the liveness schedule marks a silent machine OFFLINE (one per outage) | spec 16.2; architecture |
| `workflow_failed` | a task reaches FAILED | spec 16.2 |
| `task_blocked` | a task enters BLOCKED with `block_handler = 'owner'`, or the handler becomes `owner` (the `block_kind` is in the text) | spec 16.2 |
| `approval_required` | a task enters AWAITING_APPROVAL | spec 16.2 |
| `infrastructure_unavailable` | an infra failure class exhausts its retries (PostgreSQL, API, network) | spec 16.2; architecture |
| `backup_failed` | a backup or a restore check fails | spec 16.2 |
| `retry_limit_exceeded` | attempts, auto fixes or rework rounds reach the policy limit; also an outbox row that ran out of delivery attempts (dedup key `outbox-failed:<outbox id>`, `task_id` of the row) | spec 16.2; temporal.md "Delivery order" |
| `budget_exceeded` | a token, cost or time limit stops a run | spec 16.2; F12 |

## The Temporal databases

Temporal's server needs two databases of its own: the persistence store (workflow histories, tasks, timers) and the
visibility store (the searchable list of executions). They live on the same PostgreSQL server as the application
database and are separated from it by account, not by server, so one container, one volume and one backup cover both.

- Account: the role `af_temporal` (login, not a superuser, no `createdb`, `createrole`, `replication` or `bypassrls`)
  with its own secret file `af_temporal` (the seventh one of the secrets directory). Its password is set from that file
  by `init/lib/temporal.sql`, so a rotated secret reaches the database by running the bootstrap again, never by hand.
- Databases: `af_temporal` and `af_temporal_visibility`, both owned by `af_temporal`, with `connect` revoked from
  `PUBLIC`. As owner it may create everything Temporal's schema tool creates in them, so no other account needs a right
  there and none has one (`af_backup` included: the Temporal dumps are taken as `af_temporal`).
- Separation in both directions, held twice. First by `pg_hba.conf`: the rule for `af_temporal` names exactly the two
  databases, and the rule for the application roles names only `agent_factory`, so each side is refused by the rules
  before a password is asked. Second by privileges: `connect` on `agent_factory`, `postgres` and `template1` is held by
  nobody but the roles that need it, and `af_temporal` is none of them, and no application role holds `connect` on a
  Temporal database. A loosened rule alone therefore does not open a door. `af_bootstrap` keeps its reject rule over the
  network and reaches the Temporal databases over the local socket only, like everything else.
- One definition: the statements live in `factory/deploy/postgres/init/lib/temporal.sql`, are idempotent (the role and
  each database are made when missing, then ownership, attributes, password and the `PUBLIC` revoke are set again), and
  are run by two callers. `init/20-temporal.sh` runs them when the data directory is new. `node
  deploy/bootstrap-temporal.ts` runs the same file as `af_bootstrap` over the local socket on a data directory that
  already exists (an installation made before Temporal came, or one whose Temporal objects were changed by hand); a
  second run changes nothing, and a drifted state is repaired to the same result. It never touches the application
  database. Steps and order are in [deployment.md](deployment.md) "Adding Temporal to an existing installation".
- Checks: `deploy/verify-init.ts` proves the role's attributes, the owner and the grants of both databases, that the
  password of the secret file is the one in force, and that the two sides of the separation hold (the refusal by the rules
  and the missing `connect`); `tests/temporal-bootstrap.test.ts` runs it all on a real stack.
- Backup and restore: below, in "Migrations and backup".

- Drizzle (D27) holds the schema: definitions in `factory/db/schema/` (one file per aggregate), migrations generated by

  wrong migration is fixed by a new one. A test regenerates the schema from the definitions and fails when a

- Applied by a one-shot step with `af_migrator` before the API and control worker start, under a session advisory lock,

  A test applies the migrations one by one to an empty database and checks the schema after each file; it fails when a
  table of this document is in no file or in two (`migration-order`).
- Expand then contract (architecture): a release works with the schema before and after it; a column or value is
  removed one release after nothing reads it. Rolling code back needs no schema rollback. A contracting migration is
  preceded by an automatic backup, and its documented rollback is restore from that backup into a new database.
- A failed migration leaves the previous schema (transaction) and the services unstarted; this is the failure scenario
  "migration error" and its check.
- Backup (spec 18.1): `pg_dump` custom format of the application database, taken with `af_backup`, plus the artifact
  files. Order: artifact files are copied first, then the dump, so every artifact row of the dump has its file (storage
  keys are content-addressed and files are never changed). The two Temporal databases are dumped after the application
  database, each with `pg_dump` custom format as `af_temporal` and in its own snapshot (the one account that may read
  them), into `<name>.<database>.dump` files with a checksum each; the manifest lists them in an optional `temporal`
  section with the row counts read in the same snapshot. Both databases are in a backup or neither: a server that has
  only one is refused and repaired by the bootstrap command first, so a backup never quietly drops half of Temporal's
  history. The Temporal dumps are not one snapshot with the application dump; the reconciliation below covers that gap.
  A backup is not proof: the restore check loads it into a separate environment, restores the Temporal dumps into the
  empty databases that init made there (owned by `af_temporal`), runs the migrations to head, checks foreign keys, row
  counts of both kinds of database, artifact checksums, and the reconciliation below. Restore does the same into a new
  project.
- Reconciliation after a restore (scenario D): a restored database may lag Temporal. Outbox rows that were `done` after
  the backup are unknown, so decisions may be redelivered; this is safe because the Update id is the decision id (1:1 with its outbox row) and the
  workflow checks `used` from the decision row. `PersistTaskEvent` is idempotent by `(task_id, dedupe_key)`, so the
  workflow replays what the projection lacks. A decision confirmed to an owner after the backup point is lost with it:
  the restore procedure says so and lists the owner's decisions by the Temporal history.
