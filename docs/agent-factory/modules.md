## Phase 0 (this folder)

Design documents, plus proofs S1-S6 (testing.md). The proofs are throwaway code in the scratch area, not part of the
tree. S2 and S4 are proven. What the proofs leave open becomes tests in phase 4 (see Phase 4, Proving check): a foreign
process with the same pid, a pruned `rig exec` record, a crash before `identity.json` is written, a starter killed
without its tree. S1, S3, S5 and S6 are proven in the phase that builds on them (S6 in phase 3 against the real
proxy, with the D28 part that the trial did not cover).

The `Criterion` line of each phase below is its readiness criterion, fixed before the phase starts, and its `Proving check`
names the mandatory checks. Both are the up-front criteria of the stage-finishing rule
([governance.md](governance.md), Finishing a stage): when they pass, the phase is finished; they are not widened during
acceptance, and findings outside them become separate tasks.

The permission hook asks `POST /rights/check` for each tool call (`action` `tool`, `target` the tool name, `conditions.tool_input`); with `none` it sends `POST /rights/requests` and polls `GET /rights/requests/{id}` until the answer. It fails safe: Factory not configured, unreachable, registry off (503) or a malformed answer never allows. An ordinary session gets `ask` and one line on stderr; a Factory run gets `deny`.

Boundary interfaces (names and purpose): `RouteTable` (contracts to api, client, openapi); `Repo` (api and control to
database); `DecisionService` (record, confirm, enqueue, one transaction); `TransitionGuard` (state table in code and
in the database, same source, tested for equality); `SettingsReader` (named settings, snapshot per task run);
`RegistryService` (search, inquiry, verdict, draft, activation; the one place that applies the order of authority);
`QuestionGate` (a question in, allow or refuse with the found records out; used by the hub hook, the orchestrator and the
server).
